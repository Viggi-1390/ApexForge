# ApexForge — Backend and Database Schemas

**Version:** 1.0
**Status:** Existing and proposed schemas
**Database:** MongoDB
**Backend:** ASP.NET Core Web API, .NET 10

## 1. Purpose

Define the expected data structures, relationships, validation rules, and API contracts for ApexForge.

This document describes:

* Existing vehicle schema
* Proposed future collections
* API response expectations
* Data integrity requirements
* Telemetry import structures

**Important:** The vehicle schema already exists. The other schemas are proposed designs and must be reconciled with the repository before implementation.

## 2. General database conventions

* Use MongoDB ObjectIds as document identifiers.
* Use consistent camelCase field names in MongoDB documents.
* Use UTC timestamps for stored dates and times.
* Store units explicitly or define them unambiguously in the schema.
* Reference related documents by stable identifiers.
* Validate incoming data in the backend.
* Add indexes based on actual query patterns.
* Avoid unbounded arrays for large telemetry histories.

## 3. Existing collection: vehicles

### Purpose

Store the user's vehicle library.

### Existing document

```json
{
  "_id": "ObjectId",
  "vehicleId": 1,
  "name": "BMW M4 GT3 EVO",
  "category": "GT3",
  "horsepower": 600
}
```

`_id` is an actual MongoDB ObjectId. The string above is illustrative.

### Current C# model

```csharp
public class Vehicle
{
    public string? Id { get; set; }
    public int VehicleId { get; set; }
    public string Name { get; set; } = string.Empty;
    public string Category { get; set; } = string.Empty;
    public int Horsepower { get; set; }
}
```

The actual model uses BSON attributes to map `Id` to `_id` and preserve the existing MongoDB field names.

### Validation

* `name`: required, non-empty.
* `category`: required, non-empty.
* `horsepower`: positive integer within a sensible configured limit.
* `vehicleId`: generated by the backend and unique at the application level.
* `Id`: validate ObjectId format when used as a document ID.

Do not change the current API contract casually. If new vehicle fields are needed, introduce them compatibly.

## 4. Proposed collection: tracks

### Purpose

Store track metadata and references to track layout information.

### Proposed document

```json
{
  "_id": "ObjectId",
  "trackId": 1,
  "name": "Example Circuit",
  "location": "Example Location",
  "lengthMeters": 5000,
  "layoutSource": "unverified",
  "layoutData": null,
  "createdAtUtc": "2026-01-01T00:00:00Z",
  "updatedAtUtc": "2026-01-01T00:00:00Z"
}
```

All example values are illustrative.

### Rules

* `name` is required.
* `lengthMeters` must be positive when provided.
* Layout data must identify its source and coordinate conventions.
* Do not label an approximate or missing layout as verified.
* Large layout files may be stored separately or in file storage, with a reference kept in MongoDB.

## 5. Proposed collection: sessions

### Purpose

Represent a recording or simulation involving a selected vehicle.

### Proposed document

```json
{
  "_id": "ObjectId",
  "sessionId": 1,
  "name": "Practice Session",
  "vehicleObjectId": "ObjectId",
  "trackObjectId": "ObjectId",
  "sessionType": "recorded",
  "sourceType": "csv",
  "status": "created",
  "startedAtUtc": null,
  "createdAtUtc": "2026-01-01T00:00:00Z",
  "telemetrySampleCount": 0,
  "lapCount": 0
}
```

### Rules

* A valid vehicle reference is required.
* A track reference may be optional for sessions that do not use a defined circuit.
* `sessionType` must use an agreed set of values, such as `recorded` or `simulated`.
* `status` must use a controlled set of values.
* Sample and lap counts must reflect stored data, not estimates.
* A session should retain its identity if a vehicle's display name changes.

## 6. Proposed collection: laps

### Purpose

Store lap timing and lap-level summaries.

### Proposed document

```json
{
  "_id": "ObjectId",
  "sessionObjectId": "ObjectId",
  "lapNumber": 1,
  "startTimeSeconds": 0,
  "endTimeSeconds": 92.5,
  "lapTimeSeconds": 92.5,
  "isValid": true,
  "dataQuality": "complete"
}
```

### Rules

* `lapNumber` must be positive.
* Lap time must not be negative.
* Start and end times must be consistent.
* Invalid or incomplete laps must be represented explicitly.
* Do not infer a lap time if the source data cannot support it.

## 7. Proposed collection: telemetryPoints

### Purpose

Store individual timestamped telemetry samples.

For large sessions, telemetry samples should be stored separately from session metadata.

### Proposed document

```json
{
  "_id": "ObjectId",
  "sessionObjectId": "ObjectId",
  "lapNumber": 1,
  "sampleIndex": 0,
  "timestampSeconds": 0.0,
  "distanceMeters": 0.0,
  "speedKph": 0.0,
  "rpm": 0,
  "gear": 1,
  "throttlePercent": 0.0,
  "brakePercent": 0.0,
  "steering": 0.0,
  "lateralG": null,
  "longitudinalG": null
}
```

The example represents a proposed normalized internal format. Imported units must be converted only when the source units are known.

### Rules

* Samples must belong to a valid session.
* `sampleIndex` must be unique within a session.
* Timestamp and distance must be validated.
* Speed must not be negative unless a future data source explicitly defines a signed convention.
* Throttle and brake percentages must remain within the defined 0–100 range.
* Unknown measurements should be `null` or omitted, not replaced with fabricated values.
* Define steering units and conventions for each supported source.
* Use bulk database operations for large imports when appropriate.

## 8. Proposed collection: analysisResults

### Purpose

Store reproducible analysis outputs.

### Proposed document

```json
{
  "_id": "ObjectId",
  "sessionObjectId": "ObjectId",
  "analysisType": "lap-comparison",
  "algorithmVersion": "1.0",
  "createdAtUtc": "2026-01-01T00:00:00Z",
  "metrics": {
    "bestLapTimeSeconds": null,
    "averageSpeedKph": null
  },
  "observations": [],
  "dataQualityWarnings": []
}
```

### Rules

* Store the algorithm version.
* Identify the source session and, when relevant, the compared laps.
* Distinguish measured values from calculated metrics.
* Include data quality warnings.
* Recommendations must be traceable to the calculations that produced them.
* AI-generated observations must be identified separately if AI is introduced later.

## 9. Proposed collection: counters

The current vehicle ID generation uses a counter document.

Example:

```json
{
  "_id": "vehicleId",
  "sequence": 1
}
```

### Rules

* Use atomic increments for sequential IDs.
* Ensure the counter is initialized correctly if data is seeded or imported.
* Do not use the sequential ID as a substitute for MongoDB ObjectId.
* Use counters for other entity types only if sequential identifiers are genuinely needed.

## 10. Relationships

```text
Vehicle
  └── Sessions
        ├── Track (optional, depending on session type)
        ├── Laps
        ├── TelemetryPoints
        └── AnalysisResults
```

A session refers to a vehicle and optionally a track. Laps, telemetry points, and analysis results refer to the session.

MongoDB does not automatically enforce relational foreign keys. The backend must validate references and handle deleted or missing records.

## 11. API contracts

Existing endpoints:

| Method | Route                | Purpose                     |
| ------ | -------------------- | --------------------------- |
| GET    | `/api/vehicles`      | List vehicles               |
| POST   | `/api/vehicles`      | Create a vehicle            |
| PUT    | `/api/vehicles/{id}` | Update a vehicle            |
| DELETE | `/api/vehicles/{id}` | Delete a vehicle            |
| GET    | `/api/mongo-health`  | Check database connectivity |

Future endpoint groups, to be designed and tested when implemented:

* `/api/tracks`
* `/api/sessions`
* `/api/telemetry`
* `/api/analysis`

### API response rules

* Return consistent JSON.
* Use appropriate HTTP status codes.
* Validate all request bodies.
* Return a clear client error for invalid input.
* Avoid exposing stack traces or database internals.
* Paginate or limit large result sets.
* Do not return an entire telemetry history by default.

## 12. CSV import contract

The import pipeline should distinguish:

1. Original file metadata.
2. Source column mapping.
3. Source units.
4. Validation results.
5. Accepted samples.
6. Rejected rows and reasons.
7. Import summary.

A proposed import summary:

```json
{
  "sessionId": 1,
  "totalRows": 1000,
  "importedRows": 990,
  "rejectedRows": 10,
  "warnings": [
    "10 rows contained invalid numeric values."
  ]
}
```

This is illustrative only.

Never accept a file based solely on its extension. Validate its contents, size, headers, and values.

## 13. Indexing and performance

Potential indexes:

* Unique index for `vehicleId`.
* Index for `sessionId`.
* Index for `telemetryPoints.sessionObjectId` and `sampleIndex`.
* Index for `laps.sessionObjectId` and `lapNumber`.
* Index for `analysisResults.sessionObjectId`.

The final index definitions must be reconciled with actual identifier types and query patterns.

## 14. Schema change procedure

For every schema change:

1. Inspect existing documents and models.
2. Document the new fields and validation.
3. Decide whether existing records require migration.
4. Keep backward compatibility when practical.
5. Update API contracts and frontend usage together.
6. Test existing vehicle CRUD and affected workflows.
7. Record the change in project documentation.

Do not rename existing fields or delete data without approval.
